## P0-01 — correct exposure and reserve risk atomically — **PARTIAL**

### Sub-finding 1: notional-vs-P&L-sensitivity unit bug — **DONE**

**Real bug confirmed exactly as the brief described**: `src/run_loop.py`'s `compute_exposure()` was calling `risk_governor.usd_value_per_unit()` — a function whose job is "USD P&L per 1-unit price move" (correct for stop-distance risk sizing) — as if it answered "USD value of 1 unit of position" (notional). These coincide only for quote-is-USD FX pairs; every other case was wrong:
- USD_JPY (base=USD) at 150: reported ~$666.67 for 100,000 units instead of the real $100,000 (T01, exact match to the brief's reproduction).
- Equity/crypto (both always return 1.0 from the old function): a $200-share, 100-share position reported "$100 exposure" instead of the real $20,000 (T02, exact match).

**Consequential downstream effect found while fixing this** (not itself described by the brief's own text, but implied by it): `MAX_EQUITY_CRYPTO_NOTIONAL_PCT`'s "no-leverage ceiling" (added 2026-09-18, a previous session) reads `already_open` from this same buggy `compute_exposure()` output for equities/crypto — i.e., it was comparing a raw **share count** against a **dollar** headroom. Once a second same-direction position existed, its contribution was undercounted by orders of magnitude, silently defeating the ceiling for anything beyond a single isolated trade. Fixed by the same correction (no separate change needed — same root cause).

**Implementation**:
- `src/risk/governor.py`: new `usd_notional_per_unit(pair, price, usd_rates)`, distinct from the unchanged `usd_value_per_unit` (still correctly used everywhere else it's called — sizing, unrealized P&L, R-multiple calc).
- `src/run_loop.py`: `compute_exposure()` now calls the new function.

**Tests**: `tests/test_risk_exposure.py` (11 tests) — T01, T02 exactly, plus crypto (same bug class), quote-is-USD (unchanged-correct case), true cross pairs (uses the BASE currency's rate, not quote — a real distinction from `usd_value_per_unit`'s own cross-pair handling), and a multi-position aggregate sum.

### Sub-finding 2: correlation gate basis — **DONE**, per an explicit user decision

Fixing the notional bug above would have silently and drastically changed `MAX_CORRELATED_EXPOSURE_PCT`'s (5%) live pass/fail behavior — it consumes the same `open_positions_usd_direction` dict, and true FX/equity notional is naturally many times larger than the old buggy numbers it was implicitly calibrated against. This is exactly the kind of "consequential choice that cannot be inferred" the brief tells me to ask about rather than guess — asked via `AskUserQuestion`; user chose: **switch the gate to aggregate risk-at-stop, not notional** (matches how every other limit in `governor.py` is already expressed — 1–3% per trade, 1.5% daily, 4% weekly — so a %-of-NAV cap stays meaningful regardless of instrument leverage, unlike notional).

**Implementation**:
- `src/broker/alpaca.py`: new `get_equity_stop_price()` (equity bracket stop leg, `type="stop"` — distinct from crypto's existing `get_crypto_stop_price()`, `type="stop_limit"`) and `get_position_stop_price()` (asset-class dispatch). OANDA needed no new broker method — `open_trades()` (already existed, from Phase D2) already returns each trade's live `stopLossOrder` inline.
- `src/run_loop.py`: new `compute_correlated_stop_risk()` — aggregates USD risk-at-stop per same-USD-direction bucket. A bucket containing any position with **no live protective stop** is reported as `float('inf')` (fails closed — the gate rejects rather than silently treating unbounded risk as zero). Computed once per cycle per broker (same place `compute_exposure` already runs), threaded through `BrokerCycleContext` → `evaluate_pair` → `_evaluate_one_horizon` → `risk_governor.evaluate()`.
- `src/risk/governor.py`: `evaluate()`'s correlation gate now compares `open_positions_stop_risk_usd` (new, optional, defaults to empty) against `MAX_CORRELATED_EXPOSURE_PCT`, instead of notional. `MAX_EQUITY_CRYPTO_NOTIONAL_PCT`'s own headroom check is untouched — it's still correctly notional-based (that's the right unit for "no leverage"), and it's now actually fed correct numbers per sub-finding 1.

**PaperBroker (pure-forex-paper mode) is explicitly excluded** — it simulates fills against its own DB ledger with no real broker-side protective order to query (unlike OANDA demo / Alpaca paper, both real broker accounts). `compute_correlated_stop_risk` is skipped for it; the correlation gate falls back to its old "0 risk" default for that mode only, same practical status it always had there.

**Tests**: `tests/test_risk_governor_correlation.py` (4 tests, via an isolated in-memory SQLite engine — never the real production DB, this system has live `--auto-execute` trading) + `tests/test_compute_correlated_stop_risk.py` (7 tests, fake broker objects, no network) — cap breach, cap compliance, unprotected-position fail-closed, multi-trade aggregation, no-usd-leg exclusion, mixed protected/unprotected bucket.

### Remaining (NOT done — explicitly scoped out of this pass, tracked for continuation)

- **Candidate's own contribution not yet included in the correlation check.** The gate only evaluates *existing* open positions' risk-at-stop; it does not yet add the trade currently being evaluated. The brief's own T-test doesn't cover this specifically, but the P0-01 prose does ("Evaluate the portfolio after the proposed order"). Needs either a gate-order change (compute size before the correlation check) or a two-pass evaluation.
- **Atomic reservation is NOT built.** "Simultaneous candidates cannot exceed the configured portfolio budget" (P0-01's own acceptance criterion) requires a real reservation mechanism (claim capacity before submission, release on fill/reject/cancel/timeout) — this is a bigger, separate piece of work (likely shares infrastructure with P0-03's "one authoritative submission path" and its durable intent claim). Not attempted this pass.
- **Multi-horizon double-counting** ("coordinate multiple horizons so one market view cannot accidentally consume the same risk budget several times") — not addressed. `_evaluate_one_horizon` runs once per configured horizon per pair per cycle, each independently calling `risk_governor.evaluate()` against the SAME `stop_risk`/`exposure` snapshot (computed once per cycle) — so two horizons on the same pair, both wanting to trade the same direction, would each see the other's un-updated state and could both pass the correlation gate in the same cycle. Real gap, not yet fixed.
- **Concentration cap value (5%) is a judgment call, not derived from data** — flagged as such in the code comment; worth revisiting once real risk-at-stop numbers are observed live (currently unverifiable — the real broker accounts have no populated stop data to check this against without deploying, which is out of scope here).

## P0-02 — persistent emergency stop and coherent loss budgets — **PARTIAL**

All three findings confirmed exactly as described before fixing:

1. **Manual kill switch tied to calendar day.** The dashboard's "EMERGENCY STOP" button and `governor.py`'s own reconciliation-failure branch both called `set_kill_switch()`, writing into `risk_state`'s `(user_id, day, broker)`-scoped `kill_switch_active` flag — the SAME flag an automatic daily-loss-breach uses. A human's deliberate "stop everything" silently cleared itself at the next UTC midnight with no action from them, indistinguishable from an automatic daily guardrail resetting for a fresh day's budget (which IS correct behavior for that case).
2. **Zero baseline.** `set_kill_switch()`'s placeholder `day_start_balance=0.0` (used when it was the first write of the day, e.g. a manual stop pressed before any evaluate() cycle had run) would permanently disable that day's daily-loss check (`if day_start_balance else 0.0` guards division, but also silently zeros out `daily_pl_pct` for the rest of the day once persisted). Root cause: manual/reconciliation writes had no real NAV to seed a baseline with. Resolved as a side effect of splitting concerns below — `set_kill_switch` (day-scoped) is now ONLY ever called from inside `evaluate()`, always after a real baseline already exists.
3. **A single trade's max risk (3% ceiling) exceeds the entire daily loss limit (1.5%).** Confirmed: nothing previously stopped one maximally-confident trade from risking more than a full day's budget in one shot.

**Implementation**:
- New `manual_kill_switch` table (`src/data/db.py`) — one row per (user_id, broker), no day/week dimension, persists across restart and date rollover until explicitly cleared. Reconciliation failures now also land here (a structural "something's wrong" state, not a routine daily reset) instead of the day-scoped flag.
- New `risk_state_weekly.kill_switch_active`/`kill_switch_reason` columns — a weekly breach used to reuse the DAY-scoped flag too, so a "weekly" limit only ever actually blocked the rest of that one day, not the week. Now persists for the real remainder of the ISO week.
- `src/risk/governor.py`: new `get_manual_kill_switch`/`set_manual_kill_switch`/`set_weekly_kill_switch`; `evaluate()`'s kill-switch gate now checks manual (persistent) first, then daily (day-scoped, unchanged reset behavior — correct for an automatic daily guardrail), then weekly (now week-scoped). New remaining-daily-budget clamp in the sizing gate: a trade's own planned risk is capped to what's actually left of today's loss budget (same "gates only ever shrink a trade" philosophy as the existing notional-ceiling clamp), rather than only being caught retroactively by the kill switch on a LATER trade.
- `src/dashboard/app.py`: `get_kill_switch_state()` rewritten to combine all three sources (manual/daily/weekly) per broker; the EMERGENCY STOP/Resume buttons now use the persistent manual latch (Resume still clears all three, preserving today's actual button behavior from the user's point of view — only WHEN each layer auto-clears changed, not what pressing the button does).
- **Migration applied live**: `src/scripts/migrate_p0_02_kill_switch.py` (idempotent — additive nullable columns + a new table only, no data touched) — run against the real production database, verified via `metadata.create_all()` creating `manual_kill_switch` and `ADD COLUMN IF NOT EXISTS` adding the two `risk_state_weekly` columns. Confirmed necessary: the dashboard smoke test failed against real Postgres before this ran (`UndefinedColumn: risk_state_weekly.kill_switch_active`) and passed after.
- **Live-verified** (not just unit tests): ran `set_manual_kill_switch`/`get_manual_kill_switch`/`set_weekly_kill_switch` directly against the real production database using a fake, non-existent `user_id=999999` (never a real account) to confirm the new table/columns actually work end-to-end post-migration, then deleted those rows immediately after.

**Tests**: `tests/test_risk_governor_kill_switch.py` (8 tests, isolated in-memory SQLite) — manual latch blocks regardless of P/L, survives a simulated date rollover, clears on explicit reset; reconciliation failure sets the persistent (not daily) latch; weekly breach persists within the week and clears the following week; a single trade's risk is clamped to the remaining daily budget, and a near-zero remaining budget rejects outright.

### Remaining (NOT done — tracked for continuation)

- **UX-02's three distinct operations** ("Pause new entries" / "Cancel pending entries" / "Close positions") are explicitly out of scope here — this pass only fixed the persistence/baseline/budget backend; the dashboard still has one combined EMERGENCY STOP button, not three. That's UX-02's job, a real design task, not a quick add-on.
- **"Monitor open positions even when no new signal is produced"** — not addressed. The kill-switch/budget gates only ever run when a NEW candidate signal reaches `evaluate()`; an already-open position isn't independently re-checked against the daily/weekly budget on a quiet cycle with no new signals.
- **UI wording** was updated where it directly touches the changed mechanism (button comments, tracker) but a full "state each control's effect accurately" pass across the whole dashboard (per P0-02's own acceptance criteria) wasn't done — narrower than the brief's full ask.

## P0-03 — one authoritative submission path — **PARTIAL**

All five findings confirmed exactly as described before fixing:

1. **Manual approval relies on old risk approval.** `authorize()` reused the STORED `risk_decisions` row from signal-generation time (up to `HORIZON_TO_SECONDS`/`DEFAULT_EXPIRY_SECONDS` — as much as 4-24h old) with no re-check of CURRENT account state beyond a price-drift guard. A trade could be sent even though the kill switch had since tripped, or other trades had since pushed past max positions or the correlation cap.
2. **Truncates crypto quantity.** `size_units = int(risk["size_units"])` unconditionally — `risk_decisions.size_units` is a `Float` specifically to support crypto's genuine fractional sizing (`RiskDecision.size_units`'s own docstring), so e.g. `int(0.25)` silently became `0`.
3. **Lacks an atomic claim (T10).** A plain read-then-later-write with no lock in between — two concurrent `authorize()` calls for the same `trade_intent_id` (double-click, two tabs, a race) could both read `AWAITING_AUTHORIZATION` and both reach the broker call.
4. **Execution defaults to a fresh random client ID.** `authorize()` never passed `client_order_id` to `execute()`, so every call minted a brand-new UUID — completely defeating both this system's own `orders_fills` idempotency dedup AND the broker's own native duplicate-client-order-id protection (OANDA's `clientExtensions.id`, Alpaca's `client_order_id` — both reject/return-existing on a genuine repeat, when given the SAME id).
5. **Automatic intents marked executed regardless of status.** `run_loop.py`'s `--auto-execute` path unconditionally set `status="AUTO_EXECUTED"` even when `result.status` indicated a broker failure/rejection — indistinguishable from a real fill in the dashboard/audit trail.

**Implementation**:
- `src/authorization/service.py`: `size_units` cast only applies to non-crypto instruments (`"/" in instrument` check, matching the sizing gate's own convention). Atomic claim via `UPDATE trade_intents SET status='AUTHORIZING' WHERE id=... AND status='AWAITING_AUTHORIZATION'`, checking `rowcount==1` — exactly one concurrent caller can win; every other returns `SKIPPED` immediately, never touching the broker. A new transient `AUTHORIZING` status correctly disappears from `list_pending()` (already filtered to `AWAITING_AUTHORIZATION`) while a claim is being processed; a `_release_claim()` helper reverts it back to `AWAITING_AUTHORIZATION` on any recoverable pre-broker-call failure (no price, price drift, fresh-risk-no-longer-clears) so the intent stays retryable, matching existing behavior for those cases. Stable `client_order_id=f"intent-{trade_intent_id}"` passed explicitly to `execute()`.
- New `src/risk/governor.py` function `revalidate_before_submission()` — re-checks the PORTFOLIO-STATE-dependent gates (manual/daily/weekly kill switch, max concurrent positions, correlated risk-at-stop, equity/crypto notional ceiling) against CURRENT account state immediately before submission. Deliberately does **not** re-derive confidence/regime/track-record sizing (would let a placeholder confidence value silently re-size a trade the human already reviewed at a specific number — see the function's own docstring) — `approved_size_units` is a ceiling this can only clamp further down from, never up. Signal-quality gates (confidence/agreement/event/freshness/spread) are intentionally NOT re-verified — that's a bigger, separate change (would need the full decision pipeline re-run), tracked as a remaining gap below.
- `src/run_loop.py`'s `--auto-execute` path: same stable `client_order_id` fix, and `status` now branches on `result.status == "FILLED"` (`AUTO_EXECUTED` vs new `AUTO_EXECUTION_FAILED`), matching `authorize()`'s own existing branching.
- `src/execution/service.py`: new public `execution_mode` property (previously private-only) needed by the fresh revalidation's `compute_exposure`/`compute_correlated_stop_risk` calls.
- **Real bug caught before shipping, during test-writing**: the new fresh-revalidation code unconditionally called `_build_usd_conversion_rates()` for any `"oanda"`-kind instrument — including when the broker is `PaperBroker`, which has no `list_instruments()` (it only ever simulates fills against its own DB ledger, never a real broker's instrument catalog). Would have crashed the very first paper-mode manual approval. Guarded with the same `isinstance(broker, PaperBroker)` check already used for `compute_correlated_stop_risk`. A regression test proves this: written first with the guard removed to confirm it reproduces the exact `AttributeError`, then restored and reverified green.

**Tests**: `tests/test_authorization_service.py` (6 tests, isolated in-memory SQLite + fake broker objects, one test using a REAL `PaperBroker` instance with only its network-touching `get_current_prices` monkeypatched) — single approval places exactly one order; **two concurrent `authorize()` calls place exactly one order** (T10, directly proven via `asyncio.gather` on the real async function, not simulated); crypto fractional size survives intact; a kill switch tripped *after* signal-time approval blocks submission and reverts the intent to retryable; the PaperBroker crash is caught and fixed; rejection never touches the broker.

### Remaining (NOT done — tracked for continuation)

- **Signal-quality gates not re-verified at submission time** — confidence/agreement/event/freshness/spread remain "as good as they were at signal generation, plus the existing price-drift check." Re-deriving them properly means re-running the full decision pipeline (features, model inference, calendar lookup) at approval time — a substantially bigger change than this pass, deliberately not folded in (see `revalidate_before_submission`'s own docstring).
- **No durable submission record/outbox** — `orders_fills`' `ON CONFLICT DO NOTHING` dedup plus a stable `client_order_id` closes the most likely duplicate-order path, but P0-03's fuller ask (normalized lifecycle states: proposed/reserved/submitting/accepted/partially filled/unknown; treating a post-send timeout as "unknown" rather than inferring FILLED/failed from what a possibly-dropped response says) is not built. `ExecutionService.execute()` still returns a single synchronous result with no "unknown, reconcile later" state.
- **No unified authoritative path for manual vs. automatic** — P0-03 also asks to "route manual and automatic submissions through the same current-risk checks." They're now BOTH revalidated against fresh portfolio state, but through two separate call sites (`authorize()`'s new revalidation vs. `evaluate_pair`'s original `risk_governor.evaluate()` call) rather than one shared path — duplication risk if the two drift apart later.

## P0-04 — broker reconciliation and protective-order verification — **PARTIAL**

Two of the finding's concrete claims confirmed and fixed; the third (reconciliation itself) deliberately NOT touched this pass — see below for why.

1. **Crypto entry can finish its polling window without a stop.** Already partly handled (a timeout logs a warning and gives up cleanly) — but investigating this surfaced a WORSE, previously-undiscovered variant: `place_order()` awaited `_attach_crypto_stop_loss()` with no try/except at all. An exception raised there (e.g. a transient network error placing the actual stop order, or on the intermediate `/positions` lookup) — critically, AFTER the entry had already genuinely filled — propagated all the way up through `place_order()` into `ExecutionService.execute()`'s own try/except, which then overwrote the ENTRY order's own result with `status="ERROR:..."`. That corrupted `orders_fills` (a real fill recorded as a failure) while a real, live, UNPROTECTED crypto position sat at the broker — completely hidden from the dashboard/audit trail, arguably worse than the already-known timeout case since it looks like nothing happened at all. Fixed: the attachment call is now wrapped in its own try/except so the entry's real result can never depend on what happens next; the failure is still logged loudly (`UNPROTECTED`).
2. **Supplied crypto take-profit is not implemented.** Confirmed real, not theoretical — traced `take_profit_distance` up through `src/decision/fusion.py` (computed uniformly for every instrument, no asset-class branching) to both the manual (`authorization/service.py`) and auto-execute (`run_loop.py`) paths, both of which pass it straight into `execute(take_profit_price=...)` for crypto trades same as any other. Alpaca's crypto path silently dropped it (no bracket-order support for crypto, and unlike `stop_loss_price` there was no separate crypto take-profit attachment path at all). Fixed per the brief's own instruction ("do not imply a target exists when no order or monitored rule enforces it") — now logs a loud, explicit warning naming the exact price that is NOT being enforced, rather than silently accepting and dropping the parameter. A real monitored-exit mechanism for crypto targets was NOT built — that's a genuine feature (closer to section 5's research tracks: "Entry and exit research... stop/target/time-exit... policies"), not a quick safety patch.

**Tests**: `tests/test_alpaca_crypto_protection.py` (3 tests, a real `AlpacaBroker` instance with only `_request()` monkeypatched — proves the actual `place_order()` code path, not a reimplementation of it) — a stop-attachment exception is isolated and the entry's real status survives; take-profit-for-crypto logs the loud warning; neither param supplied produces no warnings. The exception-isolation test was written first with the fix reverted to confirm it reproduces the exact corrupted-status bug, then the fix was restored and reverified.

### Deliberately NOT done this pass: real reconciliation (`ExecutionService.reconcile()`)

The brief's core P0-04 finding — "reconciliation checks endpoint readability rather than comparing expected and actual state" — is confirmed (`reconcile()` only confirms `broker.positions()`/`broker.account_state()` don't raise; there is no comparison against anything). This was investigated but NOT fixed this pass, for a specific, considered reason:

`orders_fills` only records orders this system's OWN `ExecutionService.execute()` placed — it does NOT record broker-side stop-loss/take-profit fills (those close positions directly at the broker, never through `execute()`). A naive "sum `orders_fills.units` per instrument and compare to the broker's live position" comparison would therefore be **wrong by construction** — it would flag every single legitimate stop-loss/take-profit closure as a "reconciliation mismatch", since the closing leg is invisible to that sum. Given this session's own P0-02 work made a reconciliation failure trip the NEW **persistent** manual kill switch (correctly — that's the right design for a genuine mismatch), shipping a reconciliation check with a systematic false-positive source would mean a completely normal stop-loss fill could permanently halt trading until a human manually clears it. That's a worse outcome than today's no-op check, not a better one.

A correct comparison needs the COMPLETE execution ledger (both entries AND broker-initiated exits) — which is exactly what P1-01 ("complete execution ledger and trustworthy trade outcomes") is for. Building real reconciliation now, before P1-01, would mean either duplicating P1-01's ledger work poorly inside P0-04, or shipping a check with a known, serious false-positive risk against a live-ish trading account. Flagged here explicitly rather than silently skipped.

### Remaining (NOT done — tracked for continuation)

- **`reconcile()` itself is still a no-op beyond connectivity** — see above; blocked on (or should be sequenced with) P1-01's complete ledger.
- **No durable follow-up/retry for a failed stop attachment** — the exception is now correctly isolated and logged loudly, but there's still no automatic retry or persistent "this position needs attention" record; a human has to notice the log line. A real fix likely reuses this session's own `compute_correlated_stop_risk` (P0-01), which already DETECTS unprotected positions live every cycle via its `inf` fail-closed path — but that currently only feeds the correlation gate, not a human-visible dashboard alert.
- **No official broker precision/rules check** (P0-04's "Check current official broker rules for precision, order types, inventory, shortability, and minimums") — not investigated this pass.
- **OANDA's own reconciliation path** — this slice focused entirely on Alpaca crypto (where the two confirmed findings live); OANDA's `open_trades()`/stop-handling wasn't re-audited for the same class of exception-isolation issue.

## P0-05 — authenticated actions and account isolation — **DONE** (of the concrete findings investigated)

All findings investigated; four confirmed real and fixed, one investigated with no critical issue found.

1. **A cached user can bypass session revalidation.** Confirmed: `current_user()` just reads `st.session_state`, trusted for the ENTIRE lifetime of a live Streamlit session (a WebSocket connection spanning many reruns) with no re-check against the DB after initial login. An admin disabling a user, or a session being revoked, had zero effect on someone already mid-session until they closed the tab. Fixed with a periodic re-check (`SESSION_REVALIDATE_INTERVAL_SECONDS = 300`) — the standard middle ground between "never" (the bug) and "every single interaction" (a real, documented perf cost this project has been sensitive about elsewhere — see `get_engine()`'s own docstring). Also refreshes the cached user row on each re-check, so a role change takes effect within one window, not only at next login.
2. **Password changes do not revoke sessions.** Confirmed: `change_password()` only updated the password hash. A session token someone already held (an attacker who'd compromised the account, or another logged-in device) stayed fully valid until its normal TTL — defeating the entire point of changing a password after a suspected compromise. New `revoke_all_sessions_for_user()`, called from both `change_password()` and `set_user_status(..., "disabled")` (immediate effect rather than waiting for the periodic revalidation or the session's natural TTL).
3. **The authorization service reads intents by ID without enforcing current-user ownership.** Confirmed and serious: `trade_intent_id` is a sequential, guessable integer primary key; `authorize()`'s only protection against acting on a DIFFERENT user's pending trade was the dashboard's own `list_pending()` never showing another user's id — no server-side backstop. Worse than a read: the `broker`/`execution_service` passed in belong to whoever is CURRENTLY LOGGED IN, so a mismatch would place a real order on the WRONG user's broker account, sized/directed by another user's private signal data. Fixed with a new required `calling_user_id` parameter, checked against `intent["user_id"]` before any claim or broker interaction; raises `PermissionError` on mismatch. All 3 dashboard call sites updated to pass `CURRENT_USER_ID`.
4. **Broker host validation uses a prefix check.** Confirmed and exploitable: `_validate_alpaca_environment()` used `str.startswith("https://paper-api.alpaca.markets")` — a classic validation bypass, since `"https://paper-api.alpaca.markets.evil.com"` (an attacker-controlled subdomain) also starts with that exact string. Verified live against the actual function: the attack string passed the OLD logic and is correctly rejected by the new one. Fixed via `urllib.parse.urlparse` exact scheme+hostname match. (Currently only reachable through `.env`-set `ALPACA_BASE_URL`, admin-controlled, not live user input — `save_alpaca_credentials()`, the function this would protect if per-user Alpaca credential entry ever ships, has no caller yet. Fixed anyway: correct validation logic costs nothing and this is exactly the kind of latent gap that becomes exploitable the moment a UI is added without anyone re-auditing the validation underneath it.)
5. **Cache scoping by user for private data.** Investigated, not found to be broadly broken: spot-checked every `@st.cache_data`/`@st.cache_resource` call site in `app.py` — `cached_account_state`/`cached_alpaca_account_state` both correctly include `user_id` in their cache key (Streamlit's own arg-based keying); `cached_prices`/`cached_candles` are intentionally shared (public market data, not private); `cached_calibration_reports` is intentionally global (a model-level metric, `all_reports()` takes no `user_id` at all); `get_settings_and_engine` (`@st.cache_resource`) is intentionally process-global (DB engine/settings, not per-user data). No cross-user leak found in this pass. **Not exhaustive** — this was a spot-check of the caches most likely to carry private data, not a line-by-line audit of the full ~2500-line file.

**Real regression caught and fixed during this same pass**: shipping fix #1 (periodic revalidation) silently broke the project's own established dashboard-smoke-test pattern (`AppTest` pre-seeding only `session_state["auth_user"]`, with no real session token) — the test kept "passing" (zero exceptions) but had started silently falling back to rendering the LOGIN FORM instead of the real authenticated dashboard, since the new revalidation logic correctly treats a tokenless cached user as invalid. Caught by directly inspecting the AppTest's rendered markdown (found `"### Sign in"` where real dashboard content was expected) rather than trusting the green checkmark. **Tests**: `tests/test_auth_hardening.py` (11 tests, isolated in-memory SQLite + a `st.session_state`-level test of the real `_revalidate_if_due()` function, not a reimplementation) — exact-match URL validation (legit host passes, the exact subdomain-confusion attack is rejected, live host rejected, `None` allowed), password change revokes sessions, disabling revokes sessions, reactivating does NOT revoke, `validate_session`'s own independent disabled-user check, revalidation skips within the interval / clears on a since-revoked session / refreshes the cached user when still valid.
