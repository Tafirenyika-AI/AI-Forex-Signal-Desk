## 1. Current architecture

Python 3.12, no web framework beyond Streamlit for the dashboard. Single shared Postgres database (Neon, via `DATABASE_URL`) used by both local scheduled jobs and the dashboard, with a SQLite fallback for pure local dev (`src/data/db.py:get_engine()` — `DATABASE_URL` unset means local `data/forex.db`, matching behavior otherwise; real production always has it set). Multi-user from `src/auth/service.py`, invite-only, each user has their own encrypted broker credentials (`user_oanda_accounts`, `user_alpaca_accounts`) and preferences (`user_preferences.instrument_list_json` — the single source of truth for which instruments a user trades, across all brokers; routing to a specific broker is purely a function of the instrument string's shape, see `src/broker/registry.py`: `"_"` → OANDA/forex, `"/"` → Alpaca/crypto, bare ticker → Alpaca/equity).

**Orchestration is Windows Task Scheduler**, not a persistent daemon/queue. Each task invokes a `.bat` wrapper via `run_hidden.vbs`, which activates the venv and runs one `python -m src.scripts.X` (or `src.run_loop`) invocation, appending to its own log file under `logs/`. The core trading loop (`AIForex_DemoTradingCycle`) runs `src.run_loop --mode demo --once --auto-execute` roughly every 2 minutes; it is NOT a long-running process — each trigger is a fresh, short-lived Python process. Eleven other tasks handle data ingestion, outcome syncing, challenger scoring, meta-model training, and attribution on their own independent cadences (full state in section 13).

**Decision pipeline** (`src/run_loop.py`): per user → per broker-eligible instrument → per configured horizon (15m/1h/4h/1d) → fetch live price/candles → compute features → classify regime (`src/models/regime.py`) → compute component scores (price model, macro, cross-market, news, session, currency-strength) → `fuse()` (`src/decision/fusion.py`) blends them into a `TradeDecision` → optionally meta-model-recalibrated → risk governor (`src/risk/governor.py`) gates/sizes it → either queued for manual authorization or auto-executed via `src/execution/service.py` → broker adapter (`src/broker/alpaca.py` / `src/broker/oanda.py`) places the real order.

**Dashboard** (`src/dashboard/app.py`, Streamlit, ~2,700 lines, 14 tabs) is the human-facing surface: Mission Control (at-a-glance), Markets, Council (component votes), Signals (pending authorizations), Trades (closed-trade history + open positions), Learning, Challengers, Knowledge, Currency (forex-era, now mostly dormant), Account, Risk Center, Automation, History, and an admin/all-users view.

## 2. Existing equity capabilities

Alpaca was added as a second broker 2026-08-21/22 (paper trading only, `https://paper-api.alpaca.markets`). Covers both US equities and crypto under one adapter (`src/broker/alpaca.py`, 600+ lines). Equity entries submit as Alpaca bracket orders (entry + stop-loss + take-profit as one atomic `order_class="bracket"` request); crypto entries submit as plain market/limit orders with a protective stop attached as a *separate* order once the fill is confirmed (Alpaca rejects `bracket` for crypto outright). Candle/price data comes from Alpaca's own REST market-data endpoints (`data.alpaca.markets`), polled, not streamed (see section 5). Currently configured instrument universe (one real user): `QQQ`, `AAPL`, `MSFT`, `NVDA` (equities), `BTC/USD`, `ETH/USD` (crypto) — set directly in `user_preferences.instrument_list_json`, no dedicated onboarding UI for picking/expanding it today (the only onboarding flow in `src/dashboard/auth_gate.py` is OANDA-credential-first — a disclosed gap, see section 14).

No equity-specific data beyond price/candles exists yet: no fundamentals, no company-level news, no sector/peer context, no SEC filings. Every "intelligence" component beyond the raw price model is currently forex-only by construction (section 3) — for equities, the system has effectively been trading on the price model alone (confirmed and fixed earlier today, see section 6).

## 3. Forex-specific assumptions

Pervasive, and the majority were only fully surfaced today while fixing a live confidence bug:

- `src/models/macro_model.py:pair_macro_score`, `src/models/cross_market_model.py:pair_cross_market_score`, `src/models/news_model.py:pair_news_score` — each explicitly `if "_" not in pair: return 0.0, 0.0`. All three are base/quote **currency-differential** scores; they have no equity/crypto equivalent today, not a partial one — a hard zero, by design, every time.
- `src/models/trading_sessions.py` (session score) and `src/models/currency_strength.py` — same pattern, gated by an explicit `is_forex` check in `run_loop.py:evaluate_pair` rather than inside the function itself, but the effect is identical.
- As of today (`daecb01`), `run_loop.py`'s `component_views` construction only includes these five components for forex instruments at all — for every other asset class, `fuse()` only ever receives a `price` view. This was a real, fixed bug (see section 6), not a design choice being newly discovered here — but it means that **today, for equities/crypto, "price" is the entire model.** Everything this brief's Phases 3–9 propose building is net-new intelligence, not a gap-fill of something partially working.
- `src/models/train_meta_model.py` — trained exclusively on OANDA outcomes until today; as of `daecb01` the broker filter is removed (forex can no longer produce new linked outcomes at all, so this is moot going forward) and its feature set was narrowed from 4 components to 1 (`price` only), for the same structural reason as above.
- Calendar/economic-surprise/central-bank/CFTC-positioning ingestion (`economic_events`, `economic_surprises`, `central_bank_statements`, `cftc_positioning` tables) are forex-only *concepts* (currency-keyed, not ticker-keyed). Three of their four scheduled ingestion tasks are currently **disabled** (section 13) since OANDA/forex trading stopped entirely today; `economic_events` itself (calendar) stays active only because `pair_macro_score` reads from it — but since that function is forex-gated, it's presently feeding nothing live either.
- `src/risk/governor.py`'s correlation gate and position-sizing track-record logic are asset-class-agnostic by construction (confirmed, not assumed) — no forex-specific code there.
- The backtest engine (`src/backtest/engine.py`) stubs macro/cross_market/news/session at zero for *every* bar regardless of asset class (a different, pre-existing, disclosed reason — no point-in-time historical ingestion depth, not an asset-class gate) — but its own docstring claims this produces "zero weight" in `fuse()`, which was **not actually true** before today's fix (same dilution bug, see section 11). This affects every previously-run backtest's confidence numbers, forex included.

## 4. Crypto-specific assumptions

Narrower than forex's footprint. Crypto (`asset_class_for` returns `"crypto"` for any `"/"`-containing instrument, routed to Alpaca):
- No bracket orders (Alpaca API rejects them for crypto) — entry is a plain market/limit order; protective stop is placed as a genuinely separate order once the fill is confirmed (`AlpacaBroker._attach_crypto_stop_loss`), using `time_in_force="gtc"` (always correct, this is the behavior equities were just fixed to match — see section 11).
- No take-profit support for crypto at all (`AlpacaBroker.place_order`'s own docstring: a non-atomic second exit order racing the stop would be worse than no take-profit) — disclosed, not silently dropped (a loud warning logs when one is requested anyway, per an earlier P0-04 fix).
- `modify_stop_loss` (the Phase-D2 trailing-stop mechanism) is crypto-only — explicitly `NotImplementedError`s for equities, because canceling one leg of an equity bracket cancels the whole bracket (verified live, documented in that method's own docstring).
- Fee handling: Alpaca deducts crypto trading fees from the position's own quantity (not a separate cash line item) — `src/outcomes/alpaca_tracker.py`'s FIFO engine (built today) uses the *exit* fill's quantity as ground truth for "how much actually traded," not the nominal entry size, for exactly this reason.
- No crypto-specific intelligence (sector/fundamental/news) exists or is implied by the current architecture beyond the same price-model-only reality equities have.

## 5. Current Alpaca data flow

**Prices/candles**: pure REST polling. `AlpacaBroker.get_current_prices()` / `get_candles()` hit `data.alpaca.markets` directly, called fresh every decision cycle (no caching beyond the dashboard's own 15s `st.cache_data` layer for display purposes). No WebSocket client exists today (`src/dashboard/app.py` mentions a "stream_prices.py" script exists at `src/scripts/stream_prices.py` but — confirmed by reading it — it's a standalone diagnostic/display script, not wired into the live decision loop, and not a WebSocket client; it polls on an interval too).

**Orders**: `AlpacaBroker.place_order()` (bracket for equities, plain+separate-stop for crypto) → `ExecutionService.execute()` (`src/execution/service.py`) is the one shared entry point both the manual-authorization path (`src/authorization/service.py`) and the `--auto-execute` path in `run_loop.py` funnel through — records every attempt in `orders_fills` regardless of success/failure, with a stable `client_order_id` (`f"intent-{trade_intent_id}"`) for idempotency.

**Account/position state**: `AlpacaBroker.account_state()` / `positions()` — live REST calls, no local cache of broker-side truth (the dashboard's `cached_alpaca_account_state` wrapper is a 15s TTL purely for render performance, not a system-of-record).

**Outcome tracking**: as of today, `src/outcomes/alpaca_tracker.py` pulls Alpaca's **complete** filled-order history (`GET /v2/orders?status=all`) per sync and FIFO-matches it per instrument — this is new as of `8a8046e` (today), replacing a narrower bracket-leg-only matcher that was found to be missing most real closed trades (see section 8).

## 6. Current model architecture

- **Price model** (`src/models/price_model.py`): `sklearn.ensemble.GradientBoostingClassifier` inside a `Pipeline`, trained fresh per (instrument, horizon) pair every cycle on recent candle history (`fit()`/`predict_proba_up()`) — genuinely asset-class-agnostic, has worked for equities since Alpaca launched, untouched by anything described in this audit.
- **Regime classifier** (`src/models/regime.py`): `classify_regime()`, feature-based (ATR/trend percentiles), asset-class-agnostic.
- **Fusion** (`src/decision/fusion.py`): `fuse()` — weighted blend of whichever `ComponentView`s are passed in (today: just `price` for non-forex, all six for forex), regime-adjusted weights (`REGIME_WEIGHT_MULTIPLIERS`), a fixed action threshold, optional meta-model recalibration/veto layer.
- **Meta-model** (`src/models/train_meta_model.py`): `sklearn.linear_model.LogisticRegression`, trained on `(component_agreement, component_confidence)` pairs vs. real `WIN`/`LOSS` outcomes, `MIN_SAMPLES=30` floor, cross-validated accuracy reported (not training accuracy), auto-deploys only if it beats a majority-class-baseline-plus-margin (a real, user-approved fix from 2026-09-23, after a deployed model was found to be statistically indistinguishable from guessing the majority class). As of today, scoped to `price`-only features and applied to non-forex instruments (reversed from its original forex-only scope, since forex can no longer produce training data at all). Currently **nothing is deployed** (demoted today — the prior model was OANDA-trained and can never apply to anything again) and only 2 real linked outcomes exist against the 30 needed — the daily retrain task is re-enabled and will self-train once enough accumulate.
- **Challengers** (`src/challengers/definitions.py`): two shadow-only strategies (`economic_surprise_v1`, `ny_open_reversal_v1`), both forex-specific by construction (one reads `economic_surprises`, the other is an NY-session-open reversal signal) — effectively dormant now that forex trading has stopped, since they're never evaluated against any instrument that generates signals anymore.
- **Champion/challenger evaluation** (`src/scripts/evaluate_challengers.py`): scores champion and challenger decisions against real subsequent price data, matched-population comparison (fixed 2026-09-24, P1-05) — architecture is asset-agnostic, currently has no non-forex-relevant challengers to evaluate against.

## 7. Current risk controls

`src/risk/governor.py` — single shared gate every candidate trade passes through (`evaluate()`), asset-class-agnostic except where explicitly noted:

- **Kill switches**, three independent layers: persistent manual/reconciliation latch (`manual_kill_switch`, survives restart/date-rollover), daily loss breach (`risk_state`, resets at UTC midnight), weekly loss breach (`risk_state_weekly`, resets per ISO week) — each scoped per `(user_id, broker)`, so OANDA and Alpaca have fully independent kill-switch state.
- **Position sizing**: 1–3% risk-per-trade range (confidence scales size within that range), ATR-based stop distance, regime and per-instrument track-record both only ever *dampen* size, never boost it above the confidence-scaled baseline.
- **Correlation/exposure gate**: aggregate risk-at-stop across same-direction positions, asset-class-agnostic; a position with no live protective stop fails closed (`inf` risk) rather than being silently treated as zero.
- **Equity/crypto notional ceiling** (`MAX_EQUITY_CRYPTO_NOTIONAL_PCT`): a no-leverage cap specific to non-forex (forex is explicitly exempt — leverage there is handled by the correlation gate's own risk-at-stop math instead).
- **`MIN_CONFIDENCE=0.38`**: a hard floor below the fused confidence, tuned 2026-09-05 on forex-dominated data. As of today, confidence is computed very differently for non-forex than when that number was chosen (section 11) — **flagged, not yet recalibrated** (deliberately — see section 14).
- **Freshness/spread/event gates**: price/candle staleness thresholds, a spread-sanity check, and a calendar-event-proximity check — the last of these is forex-only by construction (same currency-keyed data as section 3).
- **Market-hours awareness**: equities only trade when the exchange is open (`is_forex_open`-equivalent gating exists per asset class in `run_loop.py`'s instrument filtering).
- Every gate above has unconditional veto power over the model's proposal — confirmed by reading `evaluate()` end to end; nothing in the sizing/confidence path can override a risk rejection.

## 8. Current outcome tracking

Two independent trackers, asymmetric history:

- **OANDA** (`src/outcomes/tracker.py`): walks OANDA's transaction ledger (`/v3/accounts/{id}/transactions/idrange`), matches `tradesClosed[]` back to the opening fill's `clientOrderID` → `authorizations.trade_intent_id`. As of today, **no longer called from the live scheduled path** (`src/scripts/sync_outcomes.py` was edited to skip it entirely) — its own code still exists and its tests still pass, but it's dead in production since forex stopped trading. A real, now-moot bug was found and fixed today: re-running it after a DB-level delete of OANDA's `trade_outcomes` rows re-inserted them, because it reads from the broker's own ledger (which doesn't forget), not a local cursor.
- **Alpaca** (`src/outcomes/alpaca_tracker.py`): rewritten today (`8a8046e`) as a proper FIFO position-matcher over Alpaca's complete filled-order history, replacing a narrower matcher that only recognized a close via its *own* originating bracket leg firing. That narrower version was found, live, to have missed most of this account's real closed trades (including one real +$8,900 winning trade) and to have mis-computed the one trade it did catch (wrong entry price, ignoring that the position had actually been built from three separate entries). The new engine reconciles real account P&L to within ~$8 of the broker's own NAV history (previously off by ~$9,400) — the closest thing this system has to "broker-verified performance" today, though it is still **internally reconstructed from the broker's raw fills**, not a native Alpaca performance API (see section 15 / Phase 1's own "internal vs. broker-verified" distinction — this is a real gap the brief's Phase 1/15 directly addresses).
- `trade_intent_id` linkage is honestly nullable throughout both trackers — when a close can't be traced back to the system's own signal (common for Alpaca right now, since most historical closes happened before today's fix and many were placed outside the normal `ExecutionService` path), it stays `NULL` rather than guessing.

## 9. Current database schema

37 tables (`src/data/db.py`, SQLAlchemy Core, no ORM). No `ForeignKey` constraints anywhere in the schema (confirmed by grep) — referential integrity is enforced by application code only, not the database. No equity-specific tables exist yet (no fundamentals, no company metadata, no ticker-keyed news) — `instrument` is a free-text string column wherever it appears, disambiguated only by its shape (`asset_class_for`). The `currencies`/forex-shaped tables (`economic_events`, `economic_surprises`, `central_bank_statements`, `cftc_positioning`) are currency-keyed and have no ticker equivalent — the brief's explicit instruction not to repurpose the `currencies` field for equities is correct and matches how little overlap actually exists today. Migrations throughout this project's history have been additive-only (new nullable columns, new tables) — no precedent for destructive schema changes other than the one explicit, user-approved, backed-up data deletion earlier today (forex trade history, not schema).

## 11. Current backtest limitations

`src/backtest/engine.py` — confirmed, disclosed gaps (from its own docstring, cross-checked against actual code):

1. **Single trade at a time** — no portfolio-level overlap, no reserved-capital modeling, no cross-position correlation during the simulated period.
2. **Flat assumed spread** (`ASSUMED_SPREAD_PIPS`, a hardcoded per-pair estimate, forex-pairs only — no equity/crypto equivalent exists, meaning a backtest run against an equity instrument today has **no cost model at all**).
3. **macro/cross_market/news/session stubbed at zero for every bar** (`STUBBED_COMPONENTS`) — for a *different* reason than the live forex-gating (no point-in-time historical ingestion depth), but with the exact same structural effect.
4. **Newly identified today, not previously known**: the stub mechanism's own docstring claims zero-confidence components get "zero weight... regardless of COMPONENT_WEIGHTS" — this was **not actually true** before today's live fix to `run_loop.py` (the same `total_weight` dilution bug, section 3/6, applied equally inside `fuse()` regardless of caller). Every backtest ever run through this engine — including the ones informing the Phase B/C/D1 model-intelligence work in this project's history — computed `combined_confidence` on the same diluted basis the live system did. The backtest's *action* decisions were unaffected (same reasoning as the live fix: a zero-confidence component never changes `combined_score`, only `combined_confidence`), but any backtest conclusion that used confidence as a filter or sizing input is affected to an unquantified degree. **Not fixed in this audit pass** — flagged for whichever later phase touches the backtest engine (the brief's own Phase 11/12).
5. Only `MIN_CONFIDENCE` is replayed from the full risk governor — spread/freshness/event/correlation/sizing/kill-switch gates are not simulated, so a backtest's trade count is an upper bound on what live trading would actually have attempted, not a prediction of it.

## 12. Code paths capable of creating, modifying, or closing an order

Enumerated by direct code read, not inference:

- `src/execution/service.py:ExecutionService.execute()` — the one shared entry point for both manual and automatic submission; calls into whichever broker adapter is configured.
- `src/broker/alpaca.py:AlpacaBroker.place_order()` (new entries), `.cancel_order()`, `.modify_stop_loss()` (crypto-only trailing-stop replace), `._attach_crypto_stop_loss()` (post-fill protective order for crypto).
- `src/broker/oanda.py:OandaBroker` — equivalent entry/modify/cancel surface (now effectively unused in production since forex stopped, but still live code).
- `src/authorization/service.py:authorize()` — the manual-approval path; atomically claims a pending `trade_intent` (`UPDATE ... WHERE status='AWAITING_AUTHORIZATION'`, single-winner on a race) before calling `ExecutionService.execute()`. Includes a fresh pre-submission risk revalidation (P0-03 work) and a cross-user ownership check (P0-05 work) — cannot act on another user's intent or stale risk approval.
- `src/run_loop.py`'s `--auto-execute` path (`_evaluate_one_horizon` → risk governor approval → `ExecutionService.execute()` directly, no human step) — this is what the `AIForex_DemoTradingCycle` scheduled task runs every ~2 minutes.
- `src/run_loop.py:_update_trailing_stops()` — the Phase D2 trailing-stop mechanism, gated behind an explicit `--enable-trailing-stops` CLI flag (off by default; not passed by the current scheduled task command line, confirmed), OANDA-demo and Alpaca-crypto only, never equities.
- **Ad-hoc verification scripts**: this session placed exactly one real order outside the normal pipeline today — the protective stop on the MSFT position, run as a one-off Python snippet, with explicit prior user approval via `AskUserQuestion`. No other out-of-band order placement occurred. (Historical note, found while investigating: several earlier closing orders for MSFT — client_order_ids that are plain UUIDs, not the system's own `intent-NNNNN` convention — were placed by *something* outside `ExecutionService` at some point before this session, never logged in `orders_fills`. Origin not established; flagged as an open question, not resolved here.)

**Nothing in this list places, modifies, or cancels an order as a side effect of starting up, reading data, migrating a table, or running a dashboard page render** — confirmed by reading every one of the above; all require an explicit call with real order parameters.

## 14. Migration risks

- **No `EQUITY_V2_ACTIVATED_AT` boundary exists yet** — this is the single most important piece of missing infrastructure for Critical Rule 0 / grandfathering. Recommended location: a new, small, additive table (e.g. `equity_v2_state`, one row) rather than a config constant, so it survives process restarts and is queryable from the dashboard, matching this project's existing pattern for small singleton state (`manual_kill_switch`-style). Not created in this audit pass — deliberately left for the first phase that actually needs it, so Phase 0 stays audit-only as instructed.
- **`src/dashboard/auth_gate.py`'s onboarding flow still hard-requires OANDA credentials** for any new user signup — a real, disclosed, pre-existing gap (noted in earlier work today) — not equity-V2-specific, but worth fixing before this brief's work makes the product equity-first in practice too.
- **`src/auth/service.py:active_trading_users()` does an INNER JOIN on `user_oanda_accounts`** — a real structural dependency that would silently exclude any future OANDA-free user from the entire scheduled cycle, Alpaca trades included. Currently mitigated only by keeping an inert OANDA credential row for the one real user — not a real fix. Directly relevant to this brief's goal of equities becoming the primary focus; should be addressed before a second, equity-only user is ever onboarded.
- **No `ForeignKey` constraints anywhere in the schema** — every join/relationship is enforced by application code only. Any new equity table (Phase 3) should decide deliberately whether to introduce real FK constraints (a schema philosophy change) or match the existing convention (indexed plain integer columns) — recommend matching the existing convention for consistency, unless a specific integrity risk justifies deviating.
- **Alpaca's news scheduled task doesn't exist yet** (`AIForex_IngestGdeltNews` is GDELT, currency-keyed, not Alpaca News/ticker-keyed) — Phase 6 needs a genuinely new ingestion path, not an extension of the existing one.
- **The forex trade-history deletion earlier today is this project's only precedent for a destructive data change** — it was explicit, user-confirmed, backed up first, and scoped to data that could never recur (forex trading stopped). It is **not** a precedent for migrations silently deleting or rewriting data; Phase 3's additive-migration instruction is consistent with how every other schema change in this project's history has been handled.
- **Real risk for Phase 2 (WebSocket market data)**: the existing polling-based price fetch is read directly, synchronously, inside the per-pair decision cycle (`evaluate_pair`) — introducing a WebSocket feed needs a clear owner for "what does `fuse()` read" during the transition (stale WebSocket data silently falling back to the existing poll, not a silent gap) — flagged for Phase 2's own design, not resolved here.

## Summary for the final deliverable's three questions (addressed now, to be revisited after each phase)

**What's already strong**: the risk governor's veto architecture (section 7), the execution path's idempotency/ownership/revalidation safeguards (section 12), the newly-fixed Alpaca outcome tracker's reconciliation accuracy (section 8), and this project's consistent practice of verifying claims against real production data before acting on them (demonstrated repeatedly in this session's own history).

**What was improved today, directly relevant to this brief**: the confidence-dilution bug (section 3/6) — not caused by this brief, but exactly the kind of "is the model's confidence actually meaningful" question Phase 10/11 depend on having a clean baseline for. The Alpaca outcome tracker rebuild (section 8) — this brief's Phase 1 (broker reconciliation engine) can now build on real, mostly-accurate data rather than needing to rediscover the same gap.

**What remains unproven**: every equity-specific intelligence source this brief proposes (fundamentals, company news, sector/peer context, cross-market equity features) — none of it exists today in any form; "price" has been the entire model for equities since Alpaca launched. The backtest engine's historical conclusions (section 11, point 4) carry an unquantified confidence-dilution effect that should be treated as an open question, not settled fact, until re-examined.

**What must happen before real capital is ever considered**: everything the brief's own Phase 20 already states — paper-only through extended verified performance, human review, explicit future decision. Nothing in this audit changes that; `src/config.py`'s live-trading refusal was not touched and should not be, per the brief's own instruction.
